# 站内通知 In-Product Notification

XBuilder 使用 In-Product Notification 在站内向用户传递异步的产品更新。Notification 是可复用的传递机制；创建通知的产品功能负责定义触发事件和通知内容。

## 背景

部分产品操作会在用户离开起始页面后完成。XBuilder 提供持久入口，让用户离开原页面后仍可查看结果。

## 目标

* 用户可以在 XBuilder 内找到发送给自己的产品更新。
* 用户可以区分未读和已读通知。
* 各产品功能共用 Notification List 和已读状态行为。

## 基本概念

### Notification

Notification 用于传递产品事件，分为两类：

* 消息 Message：发给某个 User。
* 公告 Announcement：发给发布时已存在的全体 User。之后注册的用户不会自动收到历史公告；重试发送保持原定接收范围。

两类共用相同展示结构，每位接收者的已读状态相互独立。

一个 Notification 包含：

* Recipient：可以查看 Notification 的 User
* Title：更新摘要
* Category：消息或公告
* Body：Markdown 格式的完整消息
* CreatedAt：创建时间
* ReadAt：Recipient 查看 Notification 的时间，未读时为空

### 通知列表 Notification List

Notification List 是当前用户收到的 Notification 集合，分为消息和公告两个标签，各自展示未读数量；导航入口展示两者之和。各类别按创建时间从新到旧排列，同一时间保持稳定顺序。阅读通知不改变位置，也不能使分页出现遗漏或重复。

展示内容只有标题、Markdown 正文和创建时间。用户名、作品链接、附件和引用上下文全部放在正文中，不使用事件专用展示字段。类别、标识、接收者和已读状态用于分发及交互。

Markdown 必须安全渲染：禁止可执行 HTML 和不安全的链接协议。链接不授予私有资源的访问权限。内容描述事件发生时的情况，不随用户或作品改名重写。

## 核心机制

### 创建 Notification

产品功能为 Recipient 创建 Notification。新 Notification 为未读状态，并根据 CreatedAt 显示在 Notification List 中。

### 查看 Notification

用户从导航栏打开 Notification List。打开某条 Notification 时展示详情并记录阅读时间；已读状态变化后更新未读数量。

打开列表或切换标签不标记已读。再次打开详情保留首次阅读时间。全部标为已读覆盖两个类别，包括尚未加载到面板的通知；操作快照之后送达的通知仍为未读。

区分加载中、空列表和请求失败。已读更新失败时不能让界面停留在虚假的成功状态，应允许重试。长内容在视口内仍可完整查看。关联资源后来变为私有或不可用时，保留通知历史，目标页面使用正常的权限或不可用提示，预览不能泄露受限内容。

## 建议接入的业务场景

以下是待评审确认、确认后再实现的产品方案，不代表已完成接入。建议先接点赞和 Remix。[Demo #3493](https://github.com/goplus/builder/pull/3493) 除这些互动外还演示了关注和反馈回复；其模拟数据不是正式协议。

| 事件 | 触发时机与接收者 | 重复通知规则 |
| --- | --- | --- |
| 作品点赞 | 点赞成功后，通知作品作者。 | 自赞不通知。同一操作者对同一作品最多通知一次，取消后重新点赞也不重复通知。取消点赞不撤回已有通知。 |
| 作品 Remix | 新改编作品成功保存到云端后，通知直接来源作品的作者。 | 自己改编自己的作品不通知，不逐级通知改编链上的其他作者。每个新改编作品通知一次，后续保存和重试不再通知。 |

仅成功的业务事件产生通知。失败操作、打开弹窗、未保存的本地编辑不产生通知。上线时不补发历史点赞或 Remix 通知。

按照[社区模型](./community.zh.md)，Remix 最初创建私有作品。通知可以说明操作者并链接原作品，但不能暴露私有改编作品的标题、内容或链接。本方案选择创建成功时通知，而非发布时；之后发布不再追加一条 Remix 通知。

### 内容示例

* 点赞标题：“小明点赞了你的作品”。正文：带链接的操作者名称、“点赞了你的作品”和原作品链接。
* Remix 标题：“小明改编了你的作品”。正文：带链接的操作者名称、“改编了你的作品”和原作品链接，不包含私有改编作品的信息。
* 公告标题：“系统维护通知”。正文用 Markdown 说明维护时间、受影响的功能和准备事项。

### 暂不接入的场景

* 分享：复制链接或打开分享弹窗不能证明已送达，也没有明确接收者，因此不生成通知。未来若提供“分享给指定用户”，应先定义接收者和发送成功的事件。
* 关注和反馈回复：Demo 已有展示，但触发和重复通知规则留给后续产品设计。
* 本范围不引入私聊、邮件或推送、通知偏好、事件聚合和公告发布界面。公告由可信的产品运营方编写，而非普通用户。

## 验收场景

* 一次成功点赞为作者生成一条消息；重试、取消后重新点赞和自赞不额外生成消息。
* 他人创建两个不同改编作品可以产生两条消息，重复保存不再通知，私有改编作品的信息不泄露。
* 阅读一条只减少该接收者的对应未读数量，不改变排序。
* 全部已读覆盖两个标签，之后送达的通知保持未读。
* 公告对发布时的每位接收者只送达一次，后续注册用户不补收历史副本。
* 复制链接、取消操作和失败的业务操作不产生通知。
