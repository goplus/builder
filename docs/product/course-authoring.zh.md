# 课程制作指南 Course Authoring

本文是**课程作者的操作手册**：一门课由哪些数据组成、结构化配置怎么写、以及从零制作一门课的完整流程。教程功能的产品概念（Copilot、会话、干预梯度等）见 [用户教程](./tutorial.zh.md)。

## 一门课由什么组成

一门课程（Course）包含：

* **标题**（title）与**缩略图**（thumbnail）；
* **入口**（entrypoint）：课程打开的编辑器地址，指向一个课程项目（如 `/editor/curator/Lita-Course-03/sprites/Lita/code`）。课程项目承载舞台布置、精灵、以及用户要补全的起始代码；课程内编辑运行在无副作用模式，重开课程即还原；
* **提示词**（prompt）：一段结构化文本，同时服务两个读者——**开头的 `jsonc` 配置块**给前端（机器读，课程开始瞬间生效），**其余散文**给 Copilot（当作教案读）。

课程按**系列**（Course Series）组织。系列可通过课程管理页导出为 `.xbcs.zip` 文件（内含 `course-series.json`、全部课程项目 `.xbp`、缩略图），也可从该文件导入。

## jsonc 配置块

提示词开头的第一个 ` ```jsonc ` 代码块会被前端解析为课程配置，**课程开始的瞬间即被应用，不经过 Copilot、没有任何延迟**。所有字段均可省略；解析失败等同于空配置，不会阻断开课。

```jsonc
{
  // 开课时隐藏的工作区区域；可用值见 workspace-layout 的 hideableWorkspaceAreas
  "hide": ["editor-panels", "edit-mode-switch", "preview-header", "code-editor-tools"],

  // 开课时 Copilot 面板是否展开。缺省收起（后台静默运行）；以 Copilot 为主题的课声明 "open"
  "copilot": "open",

  // 完成判定方式："code"（缺省，系统看运行输出判定）或 "copilot"（由 Copilot 判定）
  "judge": "code",

  // judge 为 "code" 时的完成信号：单次运行内，包含 log 子串的「不同输出行」达到 count 条即完成。
  // 缺省（不写 complete）时的信号是项目自行打印的完成哨兵 @@builder:course-complete@@
  "complete": {
    "log": "捡到萝卜", "count": 4,                   // 主要目标
    "require": { "code": ["repeat"], "hint": "…" }  // 次要目标（可选）
  },

  // 开课时「API References」面板收窄到的 API 集合（全课程会用到的并集，不是当前步骤的子集）
  "apis": ["step", "turn"],

  // 开场序列：进入编辑器后按书写顺序逐步播放的开场内容（引导语 / 知识点视频 / 高亮）。见下节
  "opening": [
    { "prelude": "代码已经准备好了。找到「运行」按钮并运行项目。" },
    { "video": "step" },
    { "spotlight": { "ui": "Run button" }, "tip": "点这里运行项目" }
  ]
}
```

### 开场序列 `opening`

`opening` 是一个**有序数组**，进入编辑器后按书写顺序逐步播放。它是「编辑器内开场」的唯一顺序来源：声明了 `opening` 的课，其引导语、知识点视频、高亮全部由它排布，`videos` 字段与旧的 `<course-prelude>` 弹窗都被它取代。每个条目是三种步骤之一：

| 步骤 | 写法 | 行为 |
|---|---|---|
| 引导语 | `{ "prelude": "一句话引导" }` | 弹出一个文字引导弹窗（按 **Markdown** 渲染），点「知道了」继续 |
| 知识点视频 | `{ "video": "step" }` | 播放该 API 的讲解视频（已看过的自动跳过）；条目写法同 `apis` |
| 高亮 | `{ "spotlight": { "api": "step" }, "tip": "拖它进代码" }` | 高亮一个界面元素、压暗其余，旁边显示 `tip`（可省），点击任意处后继续 |

**高亮的目标**（`spotlight`）有三种：

* `{ "api": "step" }` —— 高亮 API References 面板里的某个 API 条目，条目写法同 `apis`（裸名 / 点名 / 定义 ID，见下表）；
* `{ "ui": "Run button" }` —— 高亮一个界面地标，按其 **Radar 名**指定。常用地标：

  | Radar 名 | 元素 |
  |---|---|
  | `Run button` | 运行按钮 |
  | `Ruler` | 尺子按钮 |
  | `API References` | 左侧 API 参考面板 |
  | `Copilot trigger` | 右下角 Copilot 触发器 |
  | `Selected sprite name` | 选中精灵下方的名字标签（点击会把名字插入代码光标处） |

  （更多地标见源码里的 `v-radar={{ name: ... }}`；名字即 Radar 名。若目标一直没出现，高亮会重试数次后跳过，不会卡住序列。）
* `{ "sprite": "Boat" }` —— 高亮**编辑态舞台上的一个精灵**，按精灵名指定（舞台会给它挂一个定位框；在框内点击就会真的选中该精灵）。

目标要等**用户完成上一步操作后才会出现**的步骤，加 `"patient": true` 退出「重试数次后跳过」的默认行为。典型用法是教「点名字输入」：先高亮精灵（`{ "sprite": "Mushroom" }`），下一步带 `patient` 高亮 `Selected sprite name`——名字标签在精灵被选中后才存在，点击它即把名字插进代码。

**顺序即体验**：典型编排是「引导语 → 知识点视频 → 高亮该去点的控件」。数组为空（不写 `opening`）则回落到旧行为：`videos` 在开课后播放、`<course-prelude>` 在进编辑器前弹出。

### `apis` / 视频 / 高亮的条目写法

知识点不一定是 API。尺子是一个（`{ "video": "ruler" }`），`turn` 的数字写法也是：`turn 90` 和
`turn Right` 是**同一个函数**——spx 的 `Direction` 就是 float64，`Right` 就是常量 90——所以没有任何
definition ID 或重载能把两者分开，API 参考面板里也只有方向词那一条。第 5 课用 `{ "video": "turn" }`
教 `turn Right`，第 9 课用 `{ "video": "turn-degrees" }` 教角度。当一门课教的是某个**写法**而不是某种
能力时，就用这种形状的伪 ID；并把它登记进 `topicVideos`，否则 copilot 无法从 API 参考里发现它、也就
没法在用户问起时播放。

`apis`、`opening` 里的 `video`、以及 `spotlight` 的 `api` 目标共用同一套 API 名匹配规则。每个条目匹配 API References 面板中的条目（及其全部重载）：

| 写法 | 示例 | 匹配规则 |
|---|---|---|
| 裸名 | `step` | 点名的最后一段等于它（`Sprite.step` ✓） |
| 点名 | `Sprite.step` | 完整点名相等 |
| 带重载号 | `step#0`、`Sprite.step#0` | 在裸名/点名基础上只匹配指定重载（`#0` 即基础版） |

**不要使用完整定义 ID**（`xgo:github.com/goplus/spx/v2?...`）：它把引擎模块版本钉进了课程数据，引擎升大版本时会静默失配——spx v2→v3 升级就这样弄坏过一门课的 API 收窄。要限定重载，用上面的 `#N` 写法。

**语言结构类条目没有点名**，用它们的规范名：

| 面板条目 | 条目名 |
|---|---|
| `if condition {}` | `if_statement` |
| `if condition {} else {}` | `if_else_statement` |
| `var name type` | `var_declaration` |
| `for v in list {}` | `for_iterate` |

spx 函数（`step`、`turn`、`stepTo`、`turnTo`、`repeat`、`waitUntil`、`distanceTo`、`say`、`animateAndWait`……）以及课程项目自定义的方法（如 `IsMature`、`Water`）直接写裸名即可。

`opening` 里的 `video` 条目与 `apis` 同一套名字。视频取自全局知识点视频库（按定义 ID 索引）；同一个 API 的**任意重载都解析到同一个视频**（视频讲的是这个 API，不是某个重载），裸名也可以。库中没有的条目在演示模式下播放共用演示视频，标题取条目名。用户看过的知识点会被记住，之后的课程不再重复弹出。

**非 API 的主题视频**：编辑器工具也可以有讲解视频。目前有**尺子**（ID `xbuilder:?ruler`，裸名 `ruler` 也可以）。它不在 API 参考面板里，所以 Copilot 是从 `<api-video>` 元素的说明里知道它的——用户问「尺子怎么用」时 Copilot 会播它。想在开场就播，照常写进 `opening` 即可：`{ "video": "ruler" }`。

### 完成判定怎么选

* **`judge: "code"`（首选）**：完成与否能从游戏运行结果看出来时用它。系统直接从运行输出判定，成功对话框**即时**弹出（不等任何 LLM 往返），Copilot 随后收到「Course completed」事件、补一句评语进对话框。两种信号：
  * **`complete.log` + `count`**：适合「收集 N 个东西」类目标——游戏每达成一步打印一行（如 `捡到萝卜 Radish2`），单次运行内**不同**的匹配行数达到 `count` 即完成。重新运行会重新计数，跨运行不累计。
  * **完成哨兵（缺省）**：项目自己的逻辑判断目标达成时打印 `@@builder:course-complete@@`。适合完成条件复杂、游戏内已有判定逻辑的课。
* **`judge: "copilot"`**：完成条件**无法**从运行输出判断时才用——例如目标是「给 Copilot 发一条消息」，也就是这门课判定的是用户**说了什么**、而不是程序**做了什么**。此时在提示词里写清判定标准，Copilot 达标即弹出成功对话框（会有一次 LLM 往返的延迟，这是该模式的固有成本）。

### 主要目标与次要目标

上面的运行输出信号是**主要目标**：它说明学习者达成了目标。有些课还在意「怎么达成的」——「用 `repeat` 把四个都捡完」——
而一步步手写同样能达成目标，只看主要目标就会放过一份绕开了本课重点的答案。`complete.require` 增加一个**次要目标**，
只在主要目标达成之后才检查：

```jsonc
"complete": {
  "log": "捡到", "count": 4,
  "require": { "code": ["repeat"], "hint": "这次是一步步走完的，试着用 repeat 让它重复吧。" }
}
```

`code` 列出必须在学习者代码里**以完整单词**出现的记号；检查前会先剥掉注释和字符串字面量，所以起始代码里
「试试 repeat」这类提示本身不会让判定通过。两个目标都达成 → 照常完成本课；主要目标达成、次要目标没达成 →
不算完成，弹窗先肯定这次运行（「你的程序已经达成目标了。」）再给出 `hint`。`hint` 按 **Markdown** 渲染——
提到代码时请用反引号包起来，与应用其余部分写代码的方式保持一致。这样一来，原本只能用
`judge: "copilot"` 的「必须用了 `repeat`」也能留在零延迟的 code 判定上。

`hint` 要具体地说清还差什么；记号列表要短——它检查的是解法思路，不是代码风格评分。

### 声明了 `apis` / `opening` 的课走「快路径」

只要配置声明了 `apis` 或 `opening`（或旧的 `videos`）中的任意一个，前端就接管全部开场布置，Copilot 的开场协议随之切换为**纯静默**（只回进度判定 + 保持沉默，无需任何工具调用）——开场又快又干净。都没有声明的旧课程维持旧行为（Copilot 在开场回复里收窄面板、播放视频），行为不变但慢。**新课程一律声明**。

## 两种视频，别混淆

一门课可能出现两种视频，机制各不相同：

| 视频 | 是什么 | 怎么配 | 何时播 |
|---|---|---|---|
| **开场故事视频** | 介绍系列世界观/目标的片头，通常只有系列第一课有 | 提示词里 `<course-story-video>URL</course-story-video>` | 进入课程编辑器**之前**，片头 → 开课 → 编辑器内开场序列 |
| **知识点视频**（`opening` 的 `video` 步骤） | 某个 API 的讲解片 | `opening` 里 `{ "video": "..." }` | 进入编辑器后，按 `opening` 顺序弹出 |

API 参考的悬停卡片只展示函数签名和说明。它曾经也内嵌过讲解视频，后来撤掉了——所以课程内部只有知识点弹窗一处会播视频。

**永远不要原地覆盖视频文件。** 存储桶既不发 `Cache-Control` 也不发 `ETag`，浏览器一旦取过某个文件名，
就会按启发式过期时间一直用手里那份、不去回源——重拍的片子如果沿用旧文件名，**恰恰是看过旧版的人**会继续
看到旧版。每一版都用自己的文件名上传（`step+200.mp4`、`turn+Left.mp4`）；如果确实必须复用文件名，就得在
视频库条目里改 URL（`?v=2`）来击穿缓存。

### 开场故事视频 `<course-story-video>`

故事视频是唯一仍用标签（而非 `opening` 数组）声明的开场内容——因为它在**进编辑器之前**、开课之前就播（`opening` 是进编辑器之后的序列），且带一套专属的来源校验。在提示词里（推荐放 jsonc 块之后）写一行：

```
<course-story-video>https://<视频地址>/opening.webm</course-story-video>
```

它是系列片头（介绍世界观/目标），通常只有第一课有；与 `judge`/`apis`/`opening` 都正交（第一课没有 API，也照样能有故事视频）。

**注意 origin 白名单**：由于页面的 `?video=` 参数可被伪造，故事视频的来源被限制在——同源、`usercontentBaseUrl`（用户内容 CDN）、以及教程视频资源域名（`api-videos.ts` 里的 `tutorialVideoAssetBaseUrl`，当前是那台 S3）。放在其它域名下的 URL 会被**静默丢弃**（不报错也不播）；要换新域名，先把它加进白名单。此外，因为整站开着 `Cross-Origin-Embedder-Policy: require-corp`，跨域视频靠 `<video crossorigin>` + 桶的 CORS 才能播（三处视频位都已加）。

## 提示词的散文部分（给 Copilot 的教案）

配置块之后是给 Copilot 读的教案（开场引导语已移进配置的 `opening.prelude`，不再单独写 `<course-prelude>` 标签）。推荐的节结构（参考 Code: Lita 系列）：

```markdown
## 目标
本课教什么、为什么这样设计。教学意图写清楚，Copilot 的引导质量取决于它对课的理解。

## 当前代码
起始代码是什么、用户需要做什么改动、参考答案（注明「标准答案之一，非唯一」）。

## 完成判定（唯一标准）
judge: "code" 的课：说明完成由系统自动判定、Copilot 不要自己宣布、收到
「Course completed」事件后回一句评语即可。**不要把那句评语写进课程。** 以前课程会把成品评语原样引出来，
Copilot 就照着念——于是自己量着走到蘑菇的人，被告知「你用了 `stepTo`」。现在评语由 Copilot 按规则、
对着学习者**实际写出的代码**自己写；课程要做的是讲清教学要点，而这件事 `## 目标` 一节已经在做了。
judge: "copilot" 的课：写清 Copilot 应依据什么判定、满足后立即用成功对话框祝贺。

## 引导要点（可选）
分级引导时按什么顺序给提示、哪些时刻值得等一等、什么坑是故意留的。
```

写作要点：

* **不要**再写「开场收窄 API 到……」「开场播放……视频」「先高亮某按钮」这类节——它们已由配置的 `apis` / `opening` 声明并自动执行，散文里再写会与 Copilot 的开场协议冲突；
* 完成判定为 `code` 时，务必写明「不需要也不应由你宣布完成」，防止 Copilot 抢跳重复弹框；
* 参考答案永远注明非唯一，判定以结果为准——这决定了 Copilot 是否会错误否定用户的等价解法；
* 提示词上限 4000 字符。

## 课程依赖的场景规则

场景本身就是判定的一部分。如果场景能进入某个「目标再也不可能达成」的状态，这门课对学习者来说就是死局——
而配置里任何字段都发现不了这件事。

我们踩到的那个：随时间成熟的蘑菇是在 `onTouchStart` 里被捡起的，而这个事件只在接触**开始**的瞬间触发。
学习者如果先走到未成熟的蘑菇上、再等它成熟，这个事件早就用掉了，成熟时什么也不会发生，这一局就废了。
成熟同样是「可以被捡起」的时刻，所以蘑菇在成熟时也检查一次：

```
func harvest() { play "获得蘑菇"; println "捡到蘑菇 "+name; collected = true; die }

onTouchStart "Lita", sprite => { if mature { harvest } else { sprite.say "还没熟呢", 1 } }
// ……以及成熟的地方：
mature = true
if touching("Lita") { harvest }
```

写场景时要保证学习者能到达的每一个状态都还有出路。**优先改场景，而不是写一段散文去绕开这个尖角**——
散文只对读它的人生效，而一门课不应该必须写成参考答案那个形状才能通关。

## 制作一门新课的流程

1. **做课程项目**：布置舞台与精灵，写好起始代码（用户看到的样子），让游戏在关键进展处 `println` 出可判定的输出行（或在达成目标时打印完成哨兵）；
2. **定完成判定**：能从运行输出判断 → `judge: "code"` + `complete`（目标可以绕开本课要教的写法达成时，再加 `complete.require`）；不能 → `judge: "copilot"` + 在散文里写清标准；
3. **写配置块**：`hide` / `apis`（全课并集）/ `opening`（引导语 + 本课新知识点视频 + 该去点的控件高亮，按顺序）；
4. **写教案散文**：按上面的节结构；
5. **加入系列**并排序；导出 `.xbcs.zip` 存档。

## Code: Lita 系列现状（2026-08 重排后）

系列「Code: Lita」共 **53 课**（项目 `curator/Lita-Course-01` 至 `-53`），全部完成结构化。世界观是松鼠与蘑菇：
目标是收集蘑菇（四种颜色）与松果，项目每捡到一个就打印一行（`捡到蘑菇 <name>` / `捡到松果 <name>`），
因此同时要求两种收获的课用公共前缀计数：`complete: { "log": "捡到", "count": N }`。

单元顺序：移动基础（1–13）→ 目标与点选（14–18）→ 对象与小船（19–23）→ **循环（24–30）** → `onStart`（31）
→ **条件（32–38）**——按「观察问题（32 看运气的采摘）→ 认识提问（33 问一问蘑菇，单独学 `IsMature`）→
`if`（34）→ `if/else`（35）→ 移植新场景（36 大挑战 II）」分层，随后 `waitUntil` / `Water`（37–38）→
**「值」这条线（39–43）**：给数字起名字（39）→ 改变它（40）→ 用 `distanceTo` 得到一个值（41）→ 把值交给
`step`（42）→ 用变量存住这个值（43）→ 螺旋（44）→ 计数（45–47，`==` 落在 47 刚好数到四）→ `for` 单元
