# 用户教程 User Tutorial（新课程体系）

> 本文档是对[现有 User Tutorial 设计](./tutorial.zh.md)的修订与扩展。现有文档描述的 Copilot 驱动引导方案在本文中保留为两种课程形态之一（引导式课程）；本文档新增目标式（Playground）课程形态，并重新划分 Tutorial 与 Editor 的边界。
>
> 在上周（7月31日）的会议上，老许认为我们的现有的课程可以视为v1，然后使用ClassFramework制作的课程插件视为v2，并最终由v2取代v1。我们分析后赞成引入v2，但是不赞成用v2取代v1，并提出了v1和v2视为两种不同种类的课程的方案。
>
> 注：v1——现有的引导式课程，v2——新引入的Playground式课程。

## 背景

现有 User Tutorial 以 Copilot 为核心：课程即 Prompt（Markdown-as-course），由 Copilot 逐步引导用户完成操作。这个方案同时服务两个诉求：

1. Builder 作为 IDE 的使用引导（Product Tour）
2. （基于游戏的）编程教育

在课程实践中我们发现，对诉求 2 而言，"按步骤引导"存在固有不足：

* **学习者不需要思考。** 引导式课程把任务拆解为逐条指令，学习者只是执行指令："点这里"、"把这行改成那样"，甚至可以复制或者使用"apply"按钮。指令执行得再顺利，也不构成对概念的理解，更谈不上迁移运用。
* **没有探索空间。** 路径唯一、每一步偏离都会被纠正。学习者没有机会试错，而"试错—观察—修正"正是编程学习的核心循环，也是乐趣所在。
* **过度依赖 LLM。** 每一步推进都需要 LLM 参与，带来成本、延迟与不确定性。课程体验取决于模型每一次的临场发挥，创作者无法精确控制节奏与判定，同一门课程两次体验可能差别很大。（即先前会议提到的“抽卡感”）

老许之前提出使用ClassFramework增加确定性。
结论不是替换旧方案，而是**两类教学场景需要两种课程形态**：

* 产品操作类教学（非 Coding）：操作路径本来就唯一，按步骤引导是正确形态 → **引导式课程（v1）**
* 编程教学（Coding）：需要思考与探索，应当给目标、不给步骤 → **目标式（Playground）课程（v2）**

## 整体思路

### 两种课程形态

|  | 引导式课程 Guided Course（v1） | 目标式课程 Playground Course（v2） |
| --- | --- | --- |
| 驱动方式 | Copilot 按 Prompt 逐步引导 | 课程代码（class framework）+ 运行时判定 |
| 教学对象 | Builder 的 UI 操作 | 场景项目（一个可改造的游戏世界） |
| 场所 | 不绑定——整个 Builder 都是舞台 | 编辑器（载入场景项目） |
| 学习者做什么 | 跟随指令操作 | 在预置场景中自行探索、达成目标 |
| 通过判定 | Copilot 判断（游戏退出信号辅助） | 运行时信号 + 代码检查，确定性判定 |
| LLM 依赖 | 强（每步参与） | 弱（仅答疑与评语，可降级） |
| 典型场景 | 产品使用教学、资源操作 | 编程概念教学 |
| 创作产物 | Prompt | 场景项目 + 课程代码 |

两种形态面向的场景不同，但选择权在课程创作者：理论上也可以用引导式形态制作 Coding 课程（例如手把手完成第一行代码）。

两种形态在机制上分开支持，不做统一抽象（见[设计决策记录](#设计决策记录)）。

目标式课程内部再分两类，区别仅在编辑器形态：

* **单精灵编程课程**：专注单个精灵的代码编辑，使用单精灵模式编辑器（见下文）
* **其他（含多精灵）课程**：使用普通（标准）编辑器 UI

API 白名单、标尺等课程工具与编辑器形态无关，两类课程均可启用（见[课程工具集](#课程工具集)）。

### Tutorial 是 Editor 的插件

Tutorial 不再是散落在 Editor 内部的一组特性，而是 Editor 的一个插件：

* Editor 提供一组通用扩展点（能力），不感知 Tutorial 的存在
* Tutorial 插件消费这些扩展点，分别实现两种课程形态的 driver
* 依赖方向单向：Tutorial → Editor 扩展点；Editor 不依赖 Tutorial

这保证了 Editor 的能力（单精灵模式、API 过滤、标尺、运行时信号等）对其他潜在消费方同样可用，也使 Tutorial 可以独立演进。

## 基本概念

### 课程 Course 与课程系列 Course Series

Course 仍是核心教学单元，定义为三元组：**元数据 + 形态 + 内容**。

* **元数据**：Title、Thumbnail 等，沿用现有设计
* **形态 Type**：v1 引导式 / v2 目标式。形态只决定两件事——内容的 schema，以及由哪个 driver 驱动流程
* **内容**：v1 为 Prompt（Markdown-as-course）+ 入口 URL + References；v2 为场景项目 + 课程代码

两种形态的本质差异：**v1 教的是"操作 Builder"，对象是 UI，因此不绑定场所——首页、编辑器、社区页都可以是课程的舞台；v2 教的是"改造一个世界"，对象是场景项目，因此绑定编辑器**。

两条容易混淆的边界：

* **形态之分在于"谁驱动流程"，不在于"谁判定"**。一门 v2 课程可以把最终判定交给 Copilot（见[目标与判定](#目标与判定)），它仍是 v2：流程（开场、运行、完成）全部由课程代码驱动。
* **能力池是共享的**。spotlight、知识点视频、Copilot 等能力按 Editor 扩展点定义一次，两个 driver 各取所需：spotlight 同时服务 v1 的引导高亮与 v2 的开场步骤，知识点视频也可由 v1 中的 Copilot 按需播放。能力不专属于某个形态，避免同一能力做成两套。

**形态是 course 级属性，Course Series 对形态无感知。** Series 将一组 Course 组织为有序系列，承载：

* 课程顺序与"下一课"推进。跨形态切换（如 v1 结束在任意页面，下一课是 v2 则需跳转编辑器并载入场景项目）由 series 层的推进逻辑统一负责，两个 driver 互不感知
* 知识点的编排：每门课声明自己教授/使用的知识点，系列层面可据此审计"先用后教"等编排问题

同一系列内允许混排两种形态。典型场景：系列第 0 课用 v1 教工具（「认识编辑器」），其后为 v2 编程课程。给创作者的软性指引：系列内风格尽量统一，中途频繁切换形态会打断学习节奏。

Course Gallery、Course Admin 沿用现有设计。

### 课程包 Course Package

课程系列的存储与交换格式：将系列内全部课程的内容（课程代码 / Prompt）、场景项目与封面打包为单一文件。课程包是课程创作的一等公民，而非过渡手段：

* Course Editor 的编辑对象是课程包——如同 IDE 打开一个工程：打开的是包，编辑动作发生在其中的单门课程上（两级视图，见下）
* 同时支持在本地直接修改课程包后上传，适配不同的创作工作流（如由 AI agent 辅助批量创作与检查，配套相应的工具链）

课程包的具体内容与围绕它的创作工具，见[课程包与 Course Editor](#课程包与-course-editor)。

### 目标式课程 Playground Course（v2）

一节目标式课程 = **一个场景项目 + 一份课程代码**。课程代码基于 class framework 编写，通过调用框架能力（开场、目标与判定、课程工具、编辑器形态）完成课程编排：常见课程只是对这些能力的少量直接调用，复杂课程可以写任意的编排与判定逻辑。**不设独立的声明式配置层**——课程的一切行为都由课程代码表达。

#### 场景项目

创作者预先构建的游戏项目：舞台、精灵、以及埋好的场景代码。场景代码承担两件事：

1. 构成一个有趣、可探索的世界（学习者的改动在其中产生可见反馈）
2. 在关键事件发生时输出**完成信号**（特定日志），供判定使用

学习者与场景项目的关系遵循编辑器的通用规则：**打开属于当前账号的项目，编辑自动保存；打开不属于当前账号的项目，只读**。课程场景项目不属于学习者，Tutorial 在只读的基础上提供课程内的可编辑状态：修改仅存在于当前会话，不写回云端，因此不影响课程本身与其他学习者，学习进度（改到一半的代码）也不跨会话保留。学习者可将成果保存为自己的项目（此后即为普通的自动保存项目）。

#### 开场 Opening

课程代码在进入课程后编排一组开场步骤，每步为三种之一：

* **prelude**：一段文字（支持 Markdown），以对话框呈现——交代场景与目标
* **video**：播放一段知识点视频
* **spotlight**：高亮一个界面元素并附提示——指出本课要用的工具在哪里

每一步可以等待学习者确认后再继续，也可以自动推进。

#### 目标与判定

判定的原则：**使用代码判定结构化的结果**。

为此对可判定课程的场景设计提出一个要求：**状态转移收敛到唯一、确定的最终状态**——"完成"必须对应一个确定的状态，程序才能检查它。而检查的通道天然存在：只要程序在运行，就总能用 `println` 向控制台输出内容，因此检查游戏日志即可覆盖判定需求。

* **主要目标（做到了什么）**：课程代码监听游戏日志，等待一组完成信号——运行中输出的特定日志内容，可要求同一信号出现的次数。学习者在一次运行中集齐信号，即达成主要目标。

  选择"游戏日志"而非引擎反射能力作为信号通道：如上所述表达力足够（已覆盖全部现有课程），且实现简单、创作直观（创作者写普通游戏代码即可埋信号）。

* **次要目标（用什么方式做到）**：可选。要求学习者代码中出现指定写法（如 `stepTo`）。达成主要目标但未满足次要目标时，弹出"再试一次"提示（附创作者编写的 hint），不算通过。用于"这道题必须用本课教的概念来解"的场景。

  判定由框架提供的确定性代码检查完成（剥离注释与字符串字面量后按词匹配），不经过 LLM。

* **表达类课程**：少数课程的目标是"表达"而非"编程"（如让角色说出一句打招呼的话，说什么都对），课程代码可请求 Copilot 进行判定——这是框架能力之一，不是默认路径。

#### 课程工具集

课程工具与编辑器形态正交：单精灵模式与标准编辑器下均可启用。它们以 Editor 扩展点的形式存在，因此也不专属于 v2——进入编辑器的 v1 课程理论上同样可用。

* **API 白名单**：过滤 API Reference，只显示本课相关的 API、隐藏无关分类。一方面减小认知负担，另一方面是"本课用到什么"的显式声明，供系列层面审计知识点编排。
* **标尺 Ruler**：舞台上的度量教具，帮助学习者建立坐标与距离的直觉。

#### 单精灵模式 Single-Sprite Mode

面向单精灵编程课程的编辑器形态，把与本课无关的界面全部收起：

* 隐藏精灵列表、禁用精灵设置
* 精灵名字呈现在舞台上：悬停精灵即浮现其名字标签，点击标签将名字插入代码——学习者不必在代码里拼写精灵名
* 放大代码字号
* 运行按钮与 Copilot 入口居中放置
* 更大的 API Reference

单精灵课程运行态不自动退出，由学习者自行切换（live demo 式，鼓励反复"改一点、跑一下"）。

注：目前清清设计的整个新教程都是单精灵的，但实际上Playground教程应该也支持多精灵（标准）编辑器。

#### 知识点视频

以知识点为单位的微视频库，代替长篇文字讲解：

* 视频以 API 的 definition ID 为键组织；对非 API 的教学点（如标尺的用法、`turn` 的角度写法与方向词写法）使用专门的伪 ID
* 同一视频可被多门课程的开场引用
* Copilot 亦可按需播放：学习者问"stepTo 怎么用"时，直接以视频作答

不过我们开会的时候有提到，初七先按照课程asset实现，是否作为统一的asset还需要考虑。（便于使用，灵活度低，且画风不一定合适，还有课程级DSL——例如并非什么项目都可以使用turn Right/Flappy Bird）

#### 完成评语

课程完成时，由 LLM 基于**学习者的实际最终代码**、按少量规则生成一句话评语（使用学习者的语言、只提及其代码中出现的写法、说明做成了什么、不布置新任务）。

不使用预制评语：预制句子会被模型复述，与学习者的实际做法不符（学习者用别的写法达成目标时尤其明显）。评语生成失败时降级为通用祝贺，不阻塞完成流程。之前我们使用预制评语，这是为了解决语气之类的问题，但这样让Copilot失去了意义，且预制评语不一定真正反映了效果。

### 引导式课程 Guided Course（v1）

沿用[现有设计](./tutorial.zh.md)：课程即 Prompt，Copilot 驱动逐步引导，游戏退出信号辅助判定。修订点：

* Copilot 可以主动感知用户操作与 Builder 事件（不再"继续"按钮）（但是也可以保留，需考虑取舍）
* 优化判定通过后的输出：通过即收束，不再继续引导
* "学习者忘记退出课程、Copilot 持续感知与对话"的问题不做系统性解决：以现有的偏离感知为主，可叠加时间限制（到期提醒）
* 课程设计约束：课程流程不可重入——刷新页面或跳转外部站点后无法恢复到中间步骤，创作时应避免要求此类操作

### Copilot 的角色

两种形态中 Copilot 的定位不同：

|  | 引导式课程 | 目标式课程 |
| --- | --- | --- |
| 定位 | 驱动者：主动逐步引导 | 助手：被动待命 |
| 触发 | 进入课程即开始并持续推进 | 学习者主动求助 |
| 职责 | 高亮 UI、感知事件、判定通过 | 答疑、播放知识点视频、代码建议、完成评语 |

配套新增的 Copilot 能力（两种形态共用）：

* 禁用回复中代码块的复制（code-block copy）与一键应用（code-change apply）
* 更细致的代码修改指引工具

## 架构：Tutorial 作为 Editor 插件

Editor 提供的扩展点，按类别：

* **UI 定制**：单精灵模式开关（隐藏精灵列表、字号、布局调整）、API Reference 过滤与分类隐藏、标尺
* **运行时信号**：游戏日志流、退出码、运行开始/结束事件
* **代码访问**：读取当前代码文档（供次要目标判定与评语上下文）
* **界面引导**：spotlight 高亮与气泡提示
* **Copilot**：会话与 Topic 机制、自定义工具注册（播放视频、code apply）、主动消息
* **流程挂载**：课程进入/退出，开场、重试、完成等弹窗的挂载点

Tutorial 插件在其上实现：

* 引导式 driver：基于 Copilot Session + Prompt
* 目标式 driver：class framework——运行课程代码，向其提供开场编排、运行时信号监听、判定与完成流程等能力

## 课程包与 Course Editor

### 课程包的内容

课程包打包一个 Course Series 及其全部课程：

```
series.json          系列元数据：名称、简介、封面、课程顺序
courses/<key>/
  course.json        课程元数据：标题、封面引用、形态（v1 / v2）
  code/              v2：课程代码（开场、目标与判定、课程工具与编辑器形态的编排）
  prompt.md          v1：课程 Prompt
  project/           v2：场景项目（v1 无项目，References 以引用方式记录）
covers/              封面图
```

三个关键设计：

* **课程代码独立于场景项目。** Demo 阶段课程信息以 jsonc 块内嵌在项目代码中，是"尚无课程存储、只能从项目读取"的权宜之计；正式版中课程代码是一等数据——场景项目回归纯游戏项目，课程代码中的声明（如 API 白名单）可被审计工具静态解析。导入器保留对内嵌格式的兼容。
* **课程携带稳定 key，导入是就地更新。** 重复导入按 key 更新对应课程，而非删除重建。课程得以持续迭代，而不作废学习进度与外部链接。（Demo 阶段每次导入课程 ID 全部重新生成、进度与链接随之作废，是已被验证的痛点。）
* **知识点视频不进包。** 视频按 ID 引用、视频库独立维护：同一视频被多门课程复用，替换视频无须改动任何课程包。

### Course Editor

编辑对象是课程包（如同 IDE 打开一个工程），提供两级视图：

* **系列视图**：课程排序、系列元数据、封面管理，以及**知识点编排审计**——"先用后教"、次要目标要求未教的概念、缺少 hint 等问题以 lint 警告的形式呈现（这组检查在 Demo 阶段以脚本形式验证过价值）
* **课程视图**：按形态提供编辑器
  - v2：嵌入普通项目编辑器编辑场景项目 + 课程代码编辑（开场、目标与判定、课程工具与编辑器形态）
  - v1：Prompt 编辑器 + 入口 URL + References 管理

### Course Preview

预览即**以学习者身份运行真实的 Tutorial 插件**，不另做一套模拟实现。分两档：

* **单课预览**：改完立即以学习者视角试运行当前课程（高频）
* **系列走查**：从头过一遍系列，验证课程顺序与跨形态切换（低频）

预览需要两个开关：

* **重置学习者状态**：清空进度与已学知识点记录，保证预览可重复
* **强制会话级编辑**：作者预览自己的课程时，场景项目归属于作者，按通用规则编辑会自动保存——预览态必须豁免为会话级编辑，否则试玩会污染场景项目

### 创作工作流

Course Editor 内直接编辑，与"导出课程包 → 本地修改（可由 AI agent 辅助）→ 导入"是并行的两条通道：操作同一格式，互不排斥。

## User Story

### 学习者：完成目标式课程「点选目标」

* 学习者进入课程，编辑器以单精灵模式打开场景项目：舞台上有 Lita 和一颗蘑菇
* 开场依次进行：prelude 对话框交代任务（"让 Lita 走到蘑菇那里"）→ 播放 `stepTo` 知识点视频
* 学习者自行尝试。第一次用 `step 200` 试探，运行后发现 Lita 走过头了；改成 `step 150`，凑近了但没对准
* 学习者运行成功（场景代码检测到 Lita 碰到蘑菇，输出完成信号），但代码中没有使用本课要求的 `stepTo`——弹出"再试一次"提示，附 hint："试试点击舞台上的蘑菇，让 Lita 一步走到它面前"
* 学习者悬停舞台上的蘑菇，点击浮现的名字标签把 `Mushroom` 插入代码，写出 `stepTo Mushroom`，运行通过
* 完成弹窗出现，评语基于其最终代码生成："你用 stepTo 让 Lita 直接走到了蘑菇面前。"学习者可进入下一课或返回课程列表

期间学习者随时可以唤起 Copilot 提问；Copilot 答疑，但不主动介入。

### 创作者：制作目标式课程「点选目标」

* 构建场景项目：放置 Lita 与蘑菇，在蘑菇的代码中检测被碰到并输出完成信号日志
* 编写课程代码：
  - 开场：prelude 文案 + 引用 `stepTo` 知识点视频
  - 主要目标：等待完成信号日志（及次数）
  - 次要目标：要求代码出现 `stepTo`，附 hint 文案
  - API 白名单：本课只显示 `stepTo` 及此前已学的 API
  - 编辑器形态：单精灵模式
* 在 Course Editor 中预览（Course Preview），以学习者视角试运行整个流程
* 测试通过后发布，加入所属 Course Series

## 设计决策记录

来自评审会议的已决事项：

* **引导式课程沿用 Copilot 驱动方案**；优化判定通过后的输出。Copilot 可以主动感知。
* **两种课程形态不做统一抽象**：统一的成本高，机制上分开支持。
* **多精灵编程课程不需要单独的编辑器 UI**：复用普通模式，叠加 API 白名单与标尺。
* **单精灵课程运行态不自动退出**：由学习者自行切换，如 live demo。
* **完成信号用游戏日志，不引入 spx 反射能力**：日志已覆盖当前全部已知需求。
* **暂不支持跨课程复用项目**（同一项目以不同初始状态用于多门课程）：长期看，多个相似项目的维护成本可以通过 agent 消除。
* **"忘记退出课程"不做系统性解决**：偏离感知 + 时间限制。
* **游戏窗口比例（竖向）以后再支持。**

来自后续设计讨论的已决事项：

* **形态是 course 级属性**：Course Series 对形态无感知，系列内允许混排；跨形态切换由 series 层推进逻辑负责。
* **项目编辑遵循归属规则**：属于当前账号的项目自动保存，不属于的只读；课程内在只读基础上提供会话级可编辑状态。
* **不设独立的课程配置层**：课程能力一律由课程代码调用（class framework）；课程代码独立于场景项目，Demo 的内嵌 jsonc 仅作导入兼容。
* **课程携带稳定 key**：导入为就地更新，保护学习进度与外部链接。
* **课程包是创作的一等公民**：Course Editor 与本地工具链并行，操作同一格式。

## Demo 验证

本设计中目标式课程的核心机制已通过 Demo 分支（"Code: Lita" 系列，53 门课程）验证：

* **判定表达力**：全部 53 门课程的通过条件均可由"日志完成信号"表达；51 门使用确定性判定，2 门"表达类"课程使用 Copilot 判定
* **主要/次要目标**：7 门课程设置了次要目标（`stepTo`、`repeat`、`if` 等），"达成目标但未用指定写法 → 重试提示"的体验成立
* **知识点视频**：视频库按 definition ID 组织、伪 ID 覆盖非 API 教学点的方案可行；Copilot 按需播放已打通
* **完成评语**：规则化生成 + 拼入学习者实际代码，解决了预制评语被复述、与学习者实际做法不符的问题
* **单精灵模式**：隐藏精灵列表、舞台精灵名字标签（悬停浮现、点击插入代码）、居中运行按钮、放大 API Reference 等全套 UI 已实现
* **课程创作与分发**：以课程包导入的方式完成了 53 门课程的创作、打包、检查（知识点编排审计等）与分发，验证了课程包作为创作载体的可行性
